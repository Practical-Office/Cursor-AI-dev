Debug, Review, Architecture, Prototype

Day 4

Goal

Repeatable model-invoked disciplines for cleaning AI mess and settling design questions that cannot be answered on paper.

Why

AI creates mess at speed. Without systematic diagnosis, dual-axis review, and throwaway prototyping, teams ship the mess or invent ad-hoc cleanup every time.

Practice gate

Must-fix = a blocking review finding. Every must-fix has a committed diff before day end. A review with zero fixes is a failed exercise. Prototypes are throwaway — never harden in place.

Pre-Build agent review (taught once)

After tickets and plan exist, before Build / /implement: run a separate review agent (Grok architect preferred; a separate Cursor agent is fine) on ticket + plan. That agent must return about two concrete improvements or disagreements — not a rubber stamp. Record findings (issue comment, plan note, or CONTEXT/ADR pointer). Then proceed to implement. This is not the post-implement dual-axis closeout review below.

Core concepts

  • /diagnosing-bugs: reproduce → minimise → hypothesise → instrument → fix → regression-test. State hypothesis + next smallest experiment before changing code. Model-invoked.
  • Dual-axis /code-review (post-implement closeout; auto from /implement): (1) Spec — does the diff match the ticket/spec; (2) Standards — is the code messy vs repo conventions. Parallel sub-agents. Must-fix same day.
  • /improve-codebase-architecture: HTML report of deepenings → skill grills the selected opportunity. Reject large-rewrite proposals.
  • /prototype: throwaway answer to one design question.
    • Logic/state feel right? → LOGIC terminal app (print full state).
    • What should it look like? → UI variants on one route + floating toggle bar.
    • Rules: marked throwaway, next to real code, one command to run, no persistence default, no polish, capture verdict on throwaway branch, never harden in place.

Practice

Every must-fix committed before day end. ≥1 prototype on a throwaway branch (or clearly marked throwaway folder). Never merge to the team’s default branch. Record the verdict on the ticket.

Success criteria

Stop / Start

  • Stop leaving findings unacted. Start requiring committed fixes before close.
  • Stop settling “does this feel right?” during implement. Start /prototype first.
