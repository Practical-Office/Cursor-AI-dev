Goal

Repeatable disciplines for cleaning AI mess and settling design questions that cannot be answered on paper: model-invoked diagnosing, review, and prototype; user-invoked /improve-codebase-architecture when you choose to deepen structure.

Why

AI creates mess at speed. Without systematic diagnosis, dual-axis review, and throwaway prototyping, teams ship the mess or invent ad-hoc cleanup every time.

Practice gate

Every must-fix has a committed diff before day end. A review with zero fixes is a failed exercise. Prototypes are throwaway — never harden the shell into production code, never merge the prototype/… branch, and do not delete it after the verdict.

Core concepts

  • /diagnosing-bugs: reproduce → minimise → hypothesise → instrument → fix → regression-test. State hypothesis + next smallest experiment before changing code. Model-invoked.
  • Dual-axis /code-review: two parallel inspections —
    • Standards — repo conventions and concrete code-quality patterns (duplication, unclear naming, scattered change, etc.). Name the pattern explicitly.
    • Spec — does the diff match the originating ticket? (“no spec available” if none).
    Must-fix findings require a committed diff before you leave.
  • /improve-codebase-architecture: HTML report of deepenings → skill grills the selected opportunity. Reject large-rewrite proposals.
  • /prototype: throwaway answer to one design question. Kept as runnable evidence on a prototype/… branch, not merged and not deleted.
    • Logic or state? → one shareable HTML file (plain HTML/CSS/JS, no build). Labelled state, free-play buttons, tabbed guided walkthroughs. A non-developer can open it by double-click.
    • What should it look like? → several UI variations on one route, switchable from a floating bar and a URL parameter.
    • Rules: marked throwaway, next to the real module, trivial to run, no persistence by default, no polish. When answered, fold the validated decision into real code, commit the prototype on prototype/… (not the default branch), point at that branch from the implementation issue, and record the verdict plus the question. Do not merge the branch. Do not delete it. Do not harden the shell into production code.
  • /pr (model-invoked, not a typed chain step): when a pull request body is written, make the summary the smallest visual that shows the change, show before/after evidence that it works, and call the merge danger (one-way or two-way door, plus blast radius).
  • /retro (user-invoked close, taught as the session end on Day 5): suggestions for the agent’s environment, most severe first. Not a code change. /diagnosing-bugs does not hand off into /improve-codebase-architecture. After a fix lands, /retro asks what would have prevented the bug. Use /improve-codebase-architecture when the finding is a missing seam.

Worked example — diagnosing loop cue

Hypothesis before code

Bad: “Fix the timeout” → agent edits retry logic with no hypothesis.

Good: “Hypothesis: upstream API returns 503 under load. Next experiment: log response status on failing path only. If 503 confirmed, add circuit breaker at client seam.”

Practice

Every must-fix committed before day end. ≥1 prototype on a prototype/… branch (not the default branch), verdict and question recorded on the issue or an ADR — this satisfies Evidence Pack artifact 8. Leave the branch in place. (Pre-Build review was taught on Day 3 — apply before every /implement.)

Success criteria

Stop / Start

  • Stop leaving findings unacted. Start requiring committed fixes before close.
  • Stop settling “does this feel right?” during implement. Start /prototype first.
  • Stop merging prototype branches or deleting them after the answer. Start keeping the prototype on prototype/… and recording the verdict on the issue.
